# Тестирование на iPhone: от одобренного аккаунта до работающего туннеля

Практическая инструкция к этапам M1–M4 из [IMPLEMENTATION.md](IMPLEMENTATION.md). Всё делается
из терминала (`make …`); в Xcode заходим только добавить Apple ID и один раз «познакомить» Mac
с телефоном.

> **Главное правило отладки.** К процессу расширения **нельзя подключать отладчик Xcode**:
> Go-код Cloak под отладчиком деградирует до ~5 fps и выглядит зависшим (golang/go#57651).
> Поэтому приложение не запускается кнопкой Run из Xcode — только `make install`. Отладка — логами.

## Команды

```bash
make devices    # какие iPhone видит Mac и готовы ли они к установке
make ddi        # смонтировать на телефон образ разработчика (нужен доступ к gs.apple.com БЕЗ VPN)
make install    # make ddi + подписанная сборка → проверка entitlements → установка → запуск
make push-key   # DEBUG: доставить Secrets/my.vpnkey в приложение тем же кодом, что экран импорта
                #   негативные случаи: FORCE=1 make push-key KEY=файл-с-мусором
make logs       # забрать tunnel.log / app.log / last_error.txt в build/logs/latest/
make crashlogs  # то же + отчёты о падениях расширения и приложения (.ips)
make build      # сборка БЕЗ подписи — быстрая проверка, что всё компилируется
make framework  # собрать OpenVPNAdapter.framework из исходников с исправлением (основной способ)
make connect    # DEBUG: перезапустить приложение на телефоне и сразу подключить VPN
make disconnect # DEBUG: отключить VPN командой-файлом, без перезапуска приложения (перезапуск убил бы расширение)
make dummy      # DEBUG: профиль-пустышка M1 (диагностика без сервера; ЗАТИРАЕТ боевой профиль)
make release-check # ворота Release: DEBUG-моста нет, файлов ключа в бандле нет
```

Если к Mac подключено несколько устройств: `make install DEVICE=<udid|имя>`.

## Этап A — разовая подготовка (делает человек)

Пароли, Apple ID и подтверждения на телефоне агент вводить не может и не должен.

1. **Портал.** [developer.apple.com/account](https://developer.apple.com/account) → убедиться, что
   Membership активен (Apple Developer Program, Individual) → **принять все соглашения**
   (баннер «Review Agreement»; без этого подпись падает с «agree to the latest Program License
   Agreement») → в Membership details записать **Team ID** (10 символов). Он вписывается в
   `project.yml` → `DEVELOPMENT_TEAM`.
2. **Xcode → Settings (⌘,) → Accounts → «+» → Apple ID.** В списке команд должна быть команда
   типа **Individual**, а не только «Personal Team». Только Personal Team — значит, членство ещё
   не активировалось (бывает до 24–48 часов): выйти и войти позже.
3. **iPhone.**
   1. Подключить кабелем → «Доверять этому компьютеру» → код-пароль.
   2. Xcode → Window → Devices and Simulators (⇧⌘2) → дождаться окончания «Preparing…».
      Только после этого в настройках телефона появляется пункт про режим разработчика.
   3. Настройки → Конфиденциальность и безопасность → **Режим разработчика** → включить →
      перезагрузка → после неё подтвердить «Включить» и ввести код-пароль.
   4. Настройки → Экран и яркость → Автоблокировка → 5 мин.
4. **Другой VPN на телефоне** (AmneziaVPN и т.п.): отключить и выключить авто-подключение.
   iOS держит включённым только один VPN-профиль, и клиент с авто-подключением будет
   перехватывать сессию.
5. До конца M3 лучше выключить автообновление iOS (Основные → Обновление ПО): новая мажорная
   iOS может потребовать более новый Xcode, а тот — более новую macOS.

Проверка подготовки: `make devices` → строка `ГОТОВ: …`. Если `НЕ ГОТОВ` — под строкой написано,
чего не хватает.

> `security find-identity -v -p codesigning` после шага 2 всё ещё показывает 0 сертификатов —
> это нормально: сертификат выпускается первой подписанной сборкой.

**iOS 16 на телефоне.** `devicectl` работает только с iOS 17+. Для iOS 16: `brew install
ios-deploy`, сборка та же (блок `xcodebuild` из `scripts/install-device.sh`), установка —
`ios-deploy --id <UDID> --bundle build/DerivedData/Build/Products/Debug-iphoneos/OVoCClient.app`,
приложение открыть пальцем. `make logs` не сработает — логи только через экран «Логи» → «Поделиться».

## Этап C — первая сессия на устройстве (гейт M1 + M2)

**Что проверяем.** M1: подписи, entitlements, App Group и VPN-профиль работают на «пустышке» —
фиктивном туннеле с узким маршрутом `10.8.0.0/24`, который не трогает обычный интернет.
M2: `OpenVPNAdapter.framework` реально загружается в процессе расширения на устройстве.
Расширение уже слинковано с фреймворком, поэтому оба гейта проходят одной установкой.

1. Разблокировать телефон и оставить на домашнем экране.
2. **VPN на Mac выключить** хотя бы на время `make ddi`: сервер подписи Apple отвергает
   запросы с IP дата-центров (ошибка `3501 HTTPUnauthorized`). Смонтированный образ
   разработчика держится до перезагрузки телефона — после `PASS DDI` VPN можно включить
   обратно, если без него не открываются остальные сервисы Apple.
3. `make install`, **находясь у Mac**. При первой подписи появится диалог Связки ключей
   «codesign хочет получить доступ к ключу…» → пароль Mac → **«Всегда разрешать»**. Пока на него
   не ответить, сборка висит. Диалог может появиться несколько раз подряд.

   Почему сборка идёт «под конкретный телефон», а не `generic/platform=iOS`: у новой команды
   нет зарегистрированных устройств, а без них Apple не выпускает development-профиль. Скрипт
   собирает с `-destination id=<UDID> -allowProvisioningUpdates -allowProvisioningDeviceRegistration`
   — Xcode сам выпустит сертификат, зарегистрирует телефон, оба App ID и App Group.

   Ожидаемый вывод:
   ```
   PASS сборка: BUILD SUCCEEDED
   PASS подпись OVoCClient.app: packet-tunnel-provider + group.com.razhev.ovocclient
   PASS подпись PacketTunnel.appex: packet-tunnel-provider + group.com.razhev.ovocclient
   Подписано командой: <Team ID>
   Готово: OVoC Client установлен и запущен на «…».
   ```
4. На телефоне: **«Подключить»** → системный диалог «OVoC Client хочет добавить конфигурации
   VPN» → **Разрешить** → код-пароль / Face ID.
5. **Гейт — всё из списка должно быть правдой:**
   - [ ] статус в приложении «Подключено»; Настройки → VPN → «OVoC Client (тест)» — Подключено;
         значок VPN виден в Пункте управления (на iPhone с Face ID в статус-баре его нет);
   - [ ] Safari открывает сайты — пустышка забирает только `10.8.0.0/24`;
   - [ ] экран «Логи» → «Туннель»: шапка `App Group: OK`, строки по порядку
         `startTunnel: …` → `dummy mode…` → **`OpenVPNAdapter loaded: … from …/Frameworks/…`** →
         `memory after framework init: N MB` → `dummy tunnel is up`;
   - [ ] «Отключить» → «Отключено», значок пропал; повторное подключение работает;
   - [ ] `make logs` на Mac отдаёт те же строки; `heartbeat: memory=` заметно меньше 50 МБ
         (жёсткий лимит памяти расширения); в `app.log` нет строк `FAILED`.
6. **Негативный тест** (на свежей установке, один раз): в системном диалоге нажать «Не
   разрешать» → под кнопкой должна появиться читаемая ошибка, а не «мёртвая» кнопка.

Гейт зелёный → ветка вливается в `main`, можно идти в M3.

## Каналы отладки

| Канал | Когда | Как |
|---|---|---|
| Экран «Логи» в приложении | всегда; единственный канал у родственников | переключатель Туннель / Приложение; «Поделиться» отдаёт сразу `tunnel.log` + `app.log` (+ `last_error.txt`, если есть) |
| `make logs` | телефон подключён к Mac | файлы из App Group → `build/logs/latest/` |
| `make crashlogs` | расширение упало (код 12) | `.ips` для `PacketTunnel`, `OVoCClient`, `JetsamEvent` (убийство по памяти) |
| Console.app | нужен живой поток, или App Group не работает | выбрать iPhone слева, фильтр `subsystem:com.razhev.ovocclient`; категории `tunnel` и `app` |
| `sudo log collect --device-name "<iPhone>" --last 10m` | нужен архив системных логов | требует sudo — запускает человек |

Что пишется куда: `tunnel.log` — расширение (кольцевой, 256 КБ, heartbeat памяти раз в 30 сек);
`app.log` — приложение (загрузка профиля, ошибки сохранения, причины отключений);
`last_error.txt` — последняя фатальная ошибка туннеля, её же приложение показывает под кнопкой.

## Если что-то пошло не так

Под кнопкой приложение всегда показывает подсказку **и сырой код ошибки в квадратных скобках**.
Подсказки эвристические (строки системных ошибок Network Extension не документированы) —
при сомнениях верить коду.

### Подписанная сборка (`make install`, стадия сборки)

| Симптом | Причина | Что делать |
|---|---|---|
| «No Accounts» / «No profiles for … were found» | Apple ID не добавлен в Xcode; либо shell агента в песочнице не видит Связку ключей и аккаунт | этап A, шаг 2; запустить `make install` в своём Терминале |
| «requires a development team» | пустой `DEVELOPMENT_TEAM` | вписать Team ID в `project.yml` |
| «No Account for Team …» | опечатка в Team ID или истекла сессия Apple ID | сверить ID на портале; перелогиниться в Xcode |
| «agree to the latest Program License Agreement» | не приняты соглашения | этап A, шаг 1 |
| «Your team has no devices…» | сборка `generic/platform=iOS` до регистрации устройства | собирать только через `make install` |
| «Personal development teams … do not support Network Extensions» | выбран Team ID бесплатной Personal Team | вписать Team ID платной команды |
| «app identifier … is not available» / то же про App Group | идентификатор занят кем-то глобально | сменить `com.razhev.ovocclient` согласованно везде — полный список даёт `git grep -n ovocclient -- ':!*.md'`: `project.yml` (оба таргета), оба `.entitlements`, `SharedPaths.appGroupID`, `TunnelManager.tunnelBundleID`, `APP_BUNDLE_ID` / `APP_GROUP_ID` в `scripts/`, subsystem в `RingLogger`, домен ошибок в `PacketTunnelProvider`; затем документация. Для iOS это новое приложение — см. «Переход с PersonalVPN» |
| «provisioning profile doesn't include the … networkextension entitlement» / App Groups | capability ещё не включена на App ID | повторить `make install`; иначе портал → Identifiers → у **обоих** App ID включить Network Extensions и App Groups, привязать группу |
| сборка висит на CodeSign / `errSecInternalComponent` | ждёт диалог Связки ключей либо запущено не из GUI-сессии | пароль Mac → «Всегда разрешать»; запускать из Terminal.app |
| `FAIL подпись …` (ворота скрипта) | сборка прошла, но в подписи нет права на VPN или App Group | то же, что строкой выше про capability |
| `FAIL DDI` / «The developer disk image could not be mounted on this device» + `kAMAuthInstallErrorHTTPUnauthorized (3501)` | **VPN на Mac.** Образ разработчика персонализируется на сервере подписи Apple `gs.apple.com`, а тот отвечает `401` на запросы с IP дата-центров — при том что остальные сервисы Apple через тот же VPN работают | отключить VPN на Mac (или добавить `gs.apple.com` в исключения раздельного туннелирования) → `make ddi` → VPN можно включить обратно: образ держится до перезагрузки телефона |
| `FAIL DDI`, причина «телефон заблокирован» | телефон заблокирован в момент монтирования (скрипт ждёт разблокировки до 2 минут) | разблокировать и не гасить экран |
| `FAIL DDI`, причина не распознана | DDI из Xcode старее, чем iOS на телефоне | обновить Xcode |
| «Unable to find a destination», устройство в списке `Ineligible` | заблокирован / не нажато «Доверять» / выключен режим разработчика / ещё «Preparing» / iOS новее, чем знает Xcode | `make devices`; этап A, шаг 3; в последнем случае обновить Xcode |

| Симптом | Причина | Что делать |
|---|---|---|
| установка: `0xe8008015` | телефона нет в профиле | пересобрать через `make install` (сборка по UDID) |

| Симптом | Причина | Что делать |
|---|---|---|
| ошибка мгновенно, системного диалога не было («permission denied» / «IPC failed») | в подписи нет права на Network Extension | смотреть ворота `PASS/FAIL подпись` в выводе `make install` |

| то же, код `12` | расширение упало: dyld не нашёл фреймворк, сбой подписи фреймворка, убийство по памяти | `make crashlogs`; на телефоне: Настройки → Конфиденциальность → Аналитика → Данные аналитики → `PacketTunnel-*` |
| под кнопкой «App Group … недоступна расширению» | у appex нет App Group в подписи | ворота подписи appex в `make install`; портал → App ID расширения → App Groups |
| «Расширение туннеля не написало в лог ни строки» | расширение не запустилось либо без доступа к App Group | см. три строки выше; Console.app покажет, что именно |
| висит «Подключение…» | completion старта не вызван, NE-демон завис или другой VPN перехватывает сессию | `make logs`; удалить профиль в Настройки → VPN; перезагрузить телефон |
| экран «Логи»: `App Group НЕДОСТУПНА` | у **приложения** нет App Group в подписи | ворота подписи app в `make install` |

## Этап D — реальное VPN-соединение (M3). Только после зелёного гейта этапа C

**Подготовка (человек).** В рабочей AmneziaVPN создать **отдельный** ключ (нового клиента):
сервер OpenVPN не держит два одновременных подключения с одним сертификатом, второй клиент
выбивает первого. В окне «Поделиться»: Protocol — **OpenVPN over Cloak**, Connection format —
**«For the AmneziaVPN app»**. Только этот формат даёт ключ `vpn://…` с конфигом OpenVPN *и*
настройками Cloak; «OpenVPN native format» — это `.ovpn` без Cloak, он не подойдёт.

Сохранить, нигде не показывая: «Копировать» в Amnezia, затем на Mac

```bash
mkdir -p Secrets && pbpaste > Secrets/my.vpnkey && head -c 6 Secrets/my.vpnkey && echo && wc -c Secrets/my.vpnkey
```

Ожидаем `vpn://` и размер в несколько килобайт. Каталог `Secrets/` в `.gitignore`. Ключ содержит
приватный ключ и сертификаты: его не вставляют в чаты, код, тесты и сообщения коммитов.

**Проверить ключ, не раскрывая его:**

```bash
python3 scripts/decode-vpnkey.py --schema Secrets/my.vpnkey
```

Режим печатает только структуру: имена полей, типы, длины; адреса — лишь вид (ipv4 / loopback /
hostname); директивы `.ovpn` — имя и число аргументов; значения — только у заведомо несекретных
перечислений (`proto`, `cipher`, `Transport`, `NumConn`…). Такой вывод можно показывать в чате.
Что должно быть: контейнер `amnezia-openvpn-cloak` с секциями `openvpn` и `cloak`, в профиле
`proto tcp`, `remote <ipv4 loopback>` (это и есть Cloak), плейсхолдеры `$PRIMARY_DNS` /
`$SECONDARY_DNS`, строка `route <ipv4> 255.255.255.255 net_gateway`, блоки `<ca> <cert> <key>
<tls-auth>`, и **нет** `auth-user-pass`.

### Порядок первого боевого подключения

1. На телефоне отключить AmneziaVPN и его авто-подключение (iOS держит включённым один
   VPN-профиль). Этим ключом не должен одновременно пользоваться другой клиент.
2. `make install` — сборка с усиленным провайдером и DEBUG-мостом.
3. `make push-key` — ключ копируется в `Documents` приложения через `devicectl`, приложение
   перезапускается, импортирует ключ (ConfigKit → профиль туннеля) и **сразу удаляет файл**.
   На экране: «Ключ импортирован: …» и «Профиль: сервер».
4. «Подключить» → несколько секунд «Подключение…» (рукопожатие Cloak) → «Подключено».
5. `make logs` — агент читает `tunnel.log`. Ключевые строки: `apply OK: … autologin=true`,
   `reachability: wifi (tracking)`, `configureTunnel: remote=127.0.0.1 routes incl=… excl=…
   serverExcluded=… ipv6=sink(fd00:6f76:6f63::2/64→tunnel) dns=…`, `event: connected`,
   `memory connected: N MB`, далее `heartbeat`.

**Гейт M3 — всё должно быть правдой:**
- [ ] сайт-определитель IP показывает **IP сервера**, а не провайдера;
- [ ] сайты открываются (нет петли маршрутов, DNS идёт в туннель);
- [ ] 10 минут стабильно; `heartbeat: memory=` уверенно ниже 50 МБ;
- [ ] «Отключить» → чистое отключение; повторное подключение работает;
- [ ] тестом: сайт-определитель IPv6 не показывает адрес провайдера (утечка мимо туннеля);
- [ ] тестом: переключение Wi-Fi ↔ LTE — соединение восстанавливается или честно рвётся с
      читаемой ошибкой;
- [ ] тестом: блокировка экрана на несколько минут — после разблокировки туннель жив.

Три последних пункта — «хвост гейта M3», чек-лист с ожидаемыми строками лога — в разделе
[«Хвост гейта M3»](#хвост-гейта-m3-ipv6-смена-сети-блокировка-экрана-2026-09-26) ниже.

### Как устроена защита (что сделано перед первым запуском)

- **Состояние провайдера — на одной serial-очереди.** Система, делегат адаптера (его собственный
  поток) и сторожевые таймеры заходят на неё только через `async`: поток адаптера в это время ждёт
  наш completion, `sync` дал бы взаимоблокировку. `finishStart` / `finishStop` одноразовые —
  completion системы нельзя вызвать дважды, это убивает расширение.
- **Fail-closed.** Туннель не поднимается, если нельзя поставить `/32`-исключение для IP сервера
  (адрес не IPv4-литерал либо адаптер не выдал IPv4-настройки) или если нет ни одного
  DNS-сервера при `matchDomains = [""]`. При Cloak `tunnelRemoteAddress` равен `127.0.0.1`,
  авто-исключение iOS не срабатывает, а петля выглядит как «подключено, но трафика нет» —
  честная ошибка лучше. Причина пишется в `last_error.txt` и показывается под кнопкой.
- **`auth-user-pass` не поддерживается** — такой профиль отклоняется сразу с понятным текстом,
  а не выглядит как 30-секундный таймаут.
- **Ключ не попадает в сборку.** `make push-key` кладёт его в контейнер уже установленного
  приложения; код импорта из `Documents` существует только под `#if DEBUG` и с M4 вызывает тот
  же `TunnelManager.importKey`, что и экран. В Release/TestFlight ключ попасть не может —
  `make release-check` это проверяет.

### Итог первой попытки M3 (2026-09-20): дефект готового фреймворка — найден и исправлен

**Исправлено тем же вечером:** фреймворк теперь собирается из исходников Amnezia с патчем `patches/openvpn3-aead-auth-tag.patch` (`make framework`). С ним боевой сервер принимает пакеты телефона: 0 ошибок расшифровки, на `tun0` сервера — сотни пакетов телефона, соединение через Cloak держится без переподключений. Ниже — как искали причину.

С готовым бинарём v1.0.42 боевое подключение **не работало**, и причина найдена точно. Клиент проходит Cloak, TLS и
получает настройки, адаптер сообщает `connected` — но сервер OpenVPN на первом же пакете
данных пишет `AEAD Decrypt error: cipher final failed` → `Fatal decryption error`, сбрасывает
TCP-соединение, а клиент видит это как `Transport error … PT_SIZE_ERROR` (это метка «на все
случаи» в `ptlink.hpp` форка) и переподключается каждые 5 секунд.

Как установлено:
- Логов у боевого сервера нет (у контейнера драйвер логов `none`, OpenVPN с `--daemon` и
  `verb 1`). Без изменения сервера сообщения читаются так: `strace -f -p <pid openvpn>
  -e trace=sendto -s 300` на хосте (он пытается писать в syslog), TCP-флаги — `nsenter -t
  <pid контейнера> -n tcpdump -i lo port 1194`.
- Изоляционный тест: временный второй OpenVPN 2.5.6 в том же контейнере, прямой TCP **без
  Cloak**, свои одноразовые сертификаты, `verb 9`. Ошибка та же → Cloak и транспорт ни при чём.
- Разбор пакета по логу `verb 9` (сервер печатает ключ сеанса, IV, AD и сам пакет; первый пакет
  клиента — keepalive с известным содержимым): шифртекст клиента расшифровывается верно, ключ
  и «хвост» nonce совпадают с серверными байт в байт, а на месте 16-байтной метки подлинности
  GCM лежит **мусор из памяти** (обрывок строки PUSH_REPLY). Клиент не записывает метку.
- В исходниках форка (`amnezia-vpn/openvpn3`, версия 3.8.5 — как в нашем бинаре)
  `crypto_aead.hpp` рассчитан на метку в конце буфера и копирует её оттуда в начало, а
  mbedTLS-слой (`mbedtls_cipher_auth_encrypt`, mbed TLS 2.7.12) пишет метку по отдельному
  указателю — копирование затирает её неинициализированной памятью. Там же клиентский
  `decrypt()` вызывает *шифрование* и не проверяет метку входящих пакетов вовсе.
- Тот же симптом — amnezia-client#2072; у них лечилось перепривязкой версии ядра (март 2026).

Опровергнуто измерениями: размер пакетов/MTU, петля маршрутов (счётчик моста = 0), сжатие,
дубликат сертификата (`duplicate-cn` включён), `tunPersist`, доступность peer-info.
AES-256-CBC как обход невозможен: адаптер не даёт включить устаревшие шифры, ядро объявляет
серверу только GCM.

Из Swift это не чинится, смена протокола — не вариант (AmneziaWG в нужной сети блокируется).
Исправление — два изменения в mbedTLS-слое форка OpenVPN3: `requires_authtag_at_end()`
возвращает `false` (метку пишет старый API по отдельному указателю), а `decrypt()` вызывает
`mbedtls_cipher_auth_decrypt` и действительно проверяет метку входящих пакетов.

### Ложная фатальная ошибка #20 при отключении и двоичный мусор в `tunnel.log` (разобрано 2026-09-24)

**Симптом (сборки до 2026-09-24).** После `stopTunnel: reason=userInitiated(1)` в `tunnel.log`
шли строки `configureTunnel: clearing network settings` и
`error(fatal=true): me.ss-abramchuk.openvpn-adapter.error-domain#20 Failed to reset tunnel…`,
появлялся `last_error.txt`, а иногда между строками лога оказывалось ~140 байт двоичного мусора.
Соединение при этом отключалось штатно (`event: disconnected`).

**Откуда #20.** При разборке tun ядро OpenVPN3 зовёт `tun_builder_teardown` → у адаптера
`resetTun` (`OpenVPNAdapterImpl.mm`): он закрывает свой socketpair и вызывает делегата
`configureTunnelWithNetworkSettings:nil`; если completion пришёл с ошибкой, адаптер сообщает
**фатальную** `OpenVPNAdapterErrorTUNSetupFailed` (#20), пряча системную ошибку в
`NSUnderlyingErrorKey`. Провайдер отвечал `setTunnelNetworkSettings(nil)`, а во время
остановки iOS этот вызов отвергает — систему уже сама разбирает туннель. То есть ошибка
рождалась на ровном месте, и та же `resetTun` штатно вызывается перед каждым подключением
(`tun_builder_new`) — отсюда «clearing network settings» и до `assignIP`.

**Откуда мусор.** Это не текст ошибки (текст вложенной ошибки в лог никогда не попадал), а
ровно одна TLS-запись Cloak: заголовок `17 03 03 00 88` + 136 байт данных = 141 байт.
Go-плагин Cloak (`cmd/ck-ovpn-plugin/ck-ovpn-plugin.go` в форке amnezia-vpn/Cloak,
ветка master-amnezia) в `Cloak_close_connection` делает `syscall.Close(fd)` на номере
TCP-сокета, пойманном через `Dialer.Control`, — за спиной рантайма Go. Горутины сессии Cloak
при этом продолжают работать и пишут следующую запись в тот же номер дескриптора, который
к этому моменту получил кто-то другой в процессе. Логгер открывал файл на каждую строку, и
запись ложилась в `tunnel.log`. Плагин поставляется бинарём (`Lib/ios/arm64/ck-ovpn-plugin.a`),
в исходниках OpenVPN3 и адаптера это не лечится. Куда попадёт такая запись в другой раз,
предсказать нельзя — любой короткоживущий дескриптор процесса; порядок в ядре (`cliproto.hpp`:
сначала `tun->stop()`, потом `transport->stop()`) объясняет, почему мусор шёл уже после
наших строк об ошибке.

**Что сделано.**

- `configureTunnel(nil)` во время остановки (`phase == .stopping/.stopped`) отказ
  `setTunnelNetworkSettings(nil)` только логирует (`clearing network settings failed: <домен>#<код>
  — ignored, tunnel is stopping`) и отвечает адаптеру `nil` — ошибка #20 не рождается.
- `handleError`: фатальная ошибка обрывает сессию и пишет `last_error.txt` только в фазах
  `.starting` / `.connected`; в остальных — строка `error(fatal=true, ignored: stopping)` и всё.
- В лог от вложенной ошибки — только `underlying: <домен>#<код>`, без описания.
- `RingLogger` держит файл открытым весь срок жизни процесса: дескриптор открыт раньше любых
  сокетов и не освобождается, чужой номер ему не достанется. Ротация закрывает и открывает его заново.

**Проверка — пройдена 2026-09-26** (iPhone 16 Pro, iOS 26.6.2, сборка OVoC Client 2cd56f1+).
По дороге выяснилось, что старый `make disconnect` перезапускал приложение через devicectl
(`--terminate-existing`), а такой перезапуск убивает и процесс расширения — в `app.log`
`NEVPNConnectionErrorDomain 12`, в `tunnel.log` ни `stopTunnel`, ни строк после него (проверено и
на сборке без исправления, и после удаления второго приложения). Стоп, нажатый пальцем, доходил
штатно. Поэтому `make disconnect` теперь доставляет команду файлом `Documents/debug.disconnect`
(`scripts/debug-command.sh`): DEBUG-сборка подхватывает его раз в секунду и зовёт тот же `stop()`,
что и кнопка, без перезапуска приложения.

Штатное отключение (`make connect` → `make disconnect` → `make logs`), дословно из `tunnel.log`:
`stopTunnel: reason=userInitiated(1)` → `configureTunnel: clearing network settings (while stopping)`
→ `clearing network settings failed: NEAgentErrorDomain#1 — ignored, tunnel is stopping` →
`event: disconnected`. Ни одной `error(fatal=true)`, файл читается как UTF-8, `last_error.txt` не
создан; в `app.log` — `debug command: disconnect`, `disconnect reason: none`. Так что системная
ошибка, из которой адаптер делал «фатальную» #20, — это `NEAgentErrorDomain` код 1 на
`setTunnelNetworkSettings(nil)` во время остановки.

Негативная проверка (настоящая фатальная ошибка по-прежнему доходит до кнопки): профиль с чужим
CA (`Secrets/broken-ca.ovpn` — из ключа, `<ca>` заменён на самоподписанный) →
`make push-key KEY=Secrets/broken-ca.ovpn` → `make connect`: ядро отдаёт `VERIFY FAIL`, адаптер —
`error(fatal=true): …#48 OpenVPN fatal error occured | mbed TLS: … Certificate verification failed`
в фазе `.starting`; `last_error.txt` с этим текстом создан, приложение записало
`disconnect reason: me.ss-abramchuk.openvpn-adapter.error-domain 48` и показывает текст под
кнопкой. После проверки — `make push-key` с настоящим ключом.

**Что осталось у фреймворка.** Сырой `close` в плагине никуда не делся: запись может
попасть в любой другой свежий дескриптор. Возможная доработка — патч `fw.hpp`
(`CloakTransport::close` не звать `Cloak_close_connection`), тогда сокет за спиной Go не
закрывается вовсе; цена — локальный pipe плагина живёт до конца процесса. Не делали:
расширение и так живёт одно подключение.

### Хвост гейта M3: IPv6, смена сети, блокировка экрана (2026-09-26)

**Что было.** Расширение отдавало iOS только IPv4-настройки (`ipv6=none` в строке
`configureTunnel:`): если у сети телефона есть IPv6 (у операторов и многих домашних роутеров —
есть), всё, что резолвится в AAAA, шло мимо туннеля с настоящим адресом телефона. Смена сети и
sleep/wake были простым пробросом — ядро OpenVPN3 на iOS о смене интерфейса не узнаёт вовсе.

**Что выяснилось в исходниках фреймворка** (`OpenVPN3/openvpn/client/cliconnect.hpp`,
`OpenVPNAdapter/library/OpenVPNAdapterImpl.mm`, `OpenVPNClient.mm`):
- Объект lifecycle (сон, пробуждение, смена интерфейса) в ядре есть только для macOS
  (`MacLifeCycle`); на iOS ядро переподключается **только** по ошибке транспорта либо по
  тишине: сервер шлёт `ping 10` / `ping-restart 120`, то есть мёртвый сокет замечается не позже
  чем через 2 минуты. Переподключение — `new_client()`: событие `RECONNECTING`, новая сессия,
  `tun_builder_new` → у адаптера `resetTun` → наш `configureTunnel(nil)`, затем настройки из
  свежего PUSH_REPLY → `configureTunnel(settings)` → `CONNECTED`. `tunPersist` выключен, поэтому
  tun каждый раз собирается заново — тем же кодом, что и при первом подключении.
- `adapter.reconnect(afterTimeInterval:)` — таймер и тот же `new_client()`. `pause` — остановка
  сессии **с разборкой tun**: маршруты снимаются, и на время паузы трафик идёт мимо VPN;
  `resume` — полное рукопожатие Cloak заново. Для sleep/wake это не подходит: iOS дёргает
  их очень часто (в логах пары `sleep`/`wake` через 2–3 секунды), а разобранный tun во сне —
  утечка фонового трафика.
- IPv6-настройки адаптер строит только при `ifconfig-ipv6` от сервера; `tun_builder_set_block_ipv6`
  у адаптера — пустышка. `OpenVPNReachability` (SCNetworkReachability на главном run loop)
  в фреймворке есть, README адаптера рекомендует по её колбэку звать `reconnect`.

**Что сделано в провайдере** (`PacketTunnel/PacketTunnelProvider.swift`, `PacketFlowBridge.swift`):
- **IPv6 — в раковину.** Если сервер не дал IPv6, ставим `NEIPv6Settings` с ULA-адресом
  `fd00:6f76:6f63::2/64` и default-маршрутом IPv6 в туннель; мост отбрасывает пакеты `AF_INET6`,
  не передавая их адаптеру, и считает их (`ipv6-sunk N` в heartbeat). Почему ULA: по RFC 6724
  такой источник «не того класса» для глобальных адресатов, и iOS сама предпочитает IPv4 — сайты
  не ждут таймаута IPv6. IPv4, DNS (IPv4-литералы) и fail-closed с `/32`-исключением не задеты.
- **Смена сети.** С момента старта следим за `OpenVPNReachability`; при переходе wifi ↔ cellular
  и при возврате сети после `none` в фазе `.connected` зовём `adapter.reconnect(afterTimeInterval: 2)`.
  Без этого после LTE → Wi-Fi старый TCP-сокет Cloak жил бы через сотовую сеть.
- **Переподключение.** `.reconnecting` → `reasserting = true` (приложение: «Переподключение…»),
  `.connected` повторно → `reasserting = false`; completion старта одноразовый и второй раз не
  зовётся. `configureTunnel(nil)` (очистка перед каждым переподключением) теперь **никогда** не
  отвечает адаптеру ошибкой — отказ очистки ничего не значит, следом придут новые настройки, а
  адаптер сделал бы из него фатальную #20.
- **sleep/wake** — по-прежнему проброс (обоснование выше); на `wake` пишется, сколько спали.

**Чек-лист (руками, телефон у человека).** Перед всем: `make install`, ключ на месте,
«Подключить» → «Подключено». Логи после каждого пункта — `make logs` (телефон по кабелю).

1. **IPv6.**
   1. При поднятом VPN в Safari открыть `test-ipv6.com` (или `ipv6-test.com`).
   2. Ожидаем: IPv4 — **IP сервера**; IPv6 — «нет» / «not supported». Адреса вида `2a00:…`,
      `2001:…` домашней сети или оператора быть **не должно**.
   3. В `tunnel.log`: в `configureTunnel:` — `ipv6=sink(fd00:6f76:6f63::2/64→tunnel)`; после
      захода на сайт — `ipv6 sink: first IPv6 packet entered the tunnel and was dropped (n=…)`,
      в следующих `heartbeat` — `ipv6-sunk N` с N > 0. Если сеть телефона без IPv6, N останется 0 —
      это нормально, тест повторить в сети с IPv6 (LTE почти всегда).
   4. Контроль: отключить VPN, обновить страницу — IPv6-адрес сети появился; включить — исчез.
2. **Wi-Fi ↔ LTE.**
   1. На Wi-Fi, VPN поднят, в Safari открыт сайт-определитель IP.
   2. Пункт управления → выключить Wi-Fi. В приложении на несколько секунд «Переподключение…»,
      затем «Подключено». Обновить страницу — по-прежнему IP сервера.
   3. Включить Wi-Fi обратно — то же самое: «Переподключение…» → «Подключено».
   4. В `tunnel.log` на каждый переход: `reachability: wifi → cellular — reconnecting in 2s` (или
      `cellular → wifi`), затем `event: reconnecting`, `reconnect #1: tun→vpn … pkt …`,
      `configureTunnel: clearing network settings (reconnect #1)`, `event: assignIP`,
      `configureTunnel: … ipv6=sink(…)`, `event: connected — …`, `memory reconnected (#1): N MB`.
      Между `reconnecting` и `connected` допустимы `ovpn: Transport error`/`Client terminated,
      restarting…` (старый сокет умирает) — но не `error(fatal=true)` и не `last_error.txt`.
      Если ошибка транспорта пришла раньше колбэка reachability, порядок строк будет
      `event: reconnecting` → `reachability: …` — это тоже штатно.
   5. `app.log`: `status: Переподключение…` → `status: Подключено`, без `disconnect reason`.
3. **Блокировка экрана.**
   1. VPN поднят, заблокировать телефон кнопкой и оставить на 5–10 минут (лучше на LTE — на
      Wi-Fi iOS держит сокеты дольше).
   2. Разблокировать, открыть сайт — грузится; сайт-определитель показывает IP сервера.
   3. `tunnel.log`: `sleep` → `wake after Ns`. Дальше два штатных исхода: либо ничего — сокет
      пережил сон, `heartbeat` продолжает расти; либо в пределах 2 минут после `wake`
      `event: reconnecting` → … → `event: connected` (сокет умер, ядро переподняло сессию по
      ping-restart). Не должно быть: `error(fatal=true)`, `unexpected disconnect`, `last_error.txt`.
   4. Штатный стоп после всего: «Отключить» → `stopTunnel: reason=userInitiated(1)` →
      `event: disconnected`.

Если после смены сети ядро крутится в `Transport error` дольше минуты — снять `make logs` и
смотреть, есть ли вообще `reachability: …` строки (нет → колбэк не приходит, тогда сработает
только `ping-restart` через ≤ 2 мин) и какая ошибка у Cloak при `Cloak_dial` на новом интерфейсе.

## Этап E — импорт ключа в приложении (M4)

Ключ добавляется на экране «Добавить ключ»: вставкой из буфера (`PasteButton` — без системного
вопроса «Разрешить вставку?») или файлом из «Файлов». Можно вставить сообщение целиком — ключ
внутри найдётся сам. Первый импорт вызывает системный диалог «OVoC Client хочет добавить
конфигурации VPN» → **Разрешить** → код-пароль; «Не разрешать» даёт читаемую ошибку, прежний
профиль (если был) не портится. Смена ключа — кнопка-ключ в тулбаре; поднятый VPN при этом
сначала отключается.

**Гейт M4 (чистая установка):**
1. На Mac положить ключ в буфер, не показывая: `pbcopy < Secrets/my.vpnkey` (общий буфер
   обмена Mac ↔ iPhone: Handoff включён на обоих).
2. На телефоне удалить OVoC Client (до переименования — PersonalVPN; профиль VPN удалится вместе
   с ним) → `make install`.
3. В приложении: «Добавить ключ» → «Вставить» → «Импортировать» → «Разрешить» → код-пароль →
   «Ключ импортирован: …» → «Подключить» → сайт-определитель показывает IP сервера.
4. `make logs`: в `app.log` — `import[paste]: start` … `import OK: profile=N bytes`, ни ключа,
   ни профиля; в `tunnel.log` — `event: connected`, `heartbeat` со счётчиками пакетов, нет
   `Transport error`.

**Без рук (DEBUG-мост, тот же код):** `FORCE=1 make push-key KEY=мусор.txt` → в `app.log`
`import FAILED: parse: notAVPNKey` (обрезанный ключ — `truncated`, ключ AWG — `noCloakContainer`),
приложение не падает; `make push-key` с настоящим ключом при поднятом VPN → `tunnel is up —
stopping before profile change` → `import OK`.

## Этап F — доводка M5 на телефоне (интерфейс ru/en, ошибка под кнопкой, экспорт логов)

Что проверяем: интерфейс на языке телефона, читаемая ошибка при недоступном сервере (а не
молчаливое «Отключено»), «Поделиться» отдаёт оба лога. Сервер понадобится выключить на пару минут.

1. `make install` (Debug-сборка подойдёт: локализация и иконка в обеих конфигурациях одинаковы).
   На домашнем экране — иконка «OVoC» (щит на тёмно-синем фоне).
2. **Русский интерфейс.** Телефон на русском → главный экран: «Ключ не добавлен» / статус
   «Отключено», кнопка «Подключить», в тулбаре «Логи». Экран импорта: «Добавить ключ»,
   «Выбрать файл с ключом…», «Импортировать».
3. **Английский интерфейс** — язык всего телефона менять не нужно: Настройки → **OVoC Client**
   → **Язык** → English (пункт «Язык» iOS показывает у приложений с несколькими локализациями).
   Открыть приложение заново: «Connect», «Logs», «Add Key». Вернуть «Русский» тем же путём.
4. **Ошибка под кнопкой.** Ключ импортирован, VPN отключён. Выключить сервер (или контейнер
   Cloak/OpenVPN на нём) → «Подключить». Ожидание: «Подключение…» держится, пока расширение
   пробует соединиться (таймаут OpenVPN), затем «Отключено» и **под кнопкой красный текст**:
   подсказка + `[домен код: текст]` и/или текст из `last_error.txt` расширения. Молчаливого
   возврата в «Отключено» быть не должно. Текст выделяется и копируется. Включить сервер обратно
   → «Подключить» → «Подключено», ошибка исчезла.
5. **Экспорт логов.** «Логи» → значок «Поделиться» → в панели должны быть **два файла**
   `tunnel.log` и `app.log` (после шага 4 — ещё `last_error.txt`) → «Сохранить в Файлы» или
   отправить себе. Тот же набор файлов забирает `make logs`.
6. **Пояснения под статусом.** Переключить Wi-Fi ↔ LTE при поднятом VPN: на время
   «Переподключение…» под статусом — «Сеть изменилась — соединение восстанавливается…».
   Удалить профиль в Настройки → VPN при открытом приложении: статус «Нет профиля VPN» с
   подсказкой «…Импортируйте ключ заново», кнопка-ключ в тулбаре → импорт.
7. В `app.log` при этом — только английские строки (`status: connecting`, `disconnect reason: …`):
   лог не локализуется намеренно, чтобы читался одинаково с любого телефона.

## Переход с PersonalVPN на OVoC Client (2026-09-24)

С переименованием сменился bundle ID: `com.razhev.personalvpn` → `com.razhev.ovocclient`
(расширение `com.razhev.ovocclient.tunnel`, App Group `group.com.razhev.ovocclient`). Для iOS это
другое приложение: поверх старого оно не встанет, а появится рядом. Один раз:

1. На телефоне удалить старое **PersonalVPN**: удерживать иконку → «Удалить приложение» →
   «Удалить». Вместе с ним удалятся его VPN-профиль и логи в старой App Group; то, что уже скачано
   в `build/logs/`, остаётся.
2. `make install`. Первая подпись с новым bundle ID сама заведёт на портале два App ID и App Group
   (как в M1). Ожидаемо: `PASS подпись OVoCClient.app: … + group.com.razhev.ovocclient`. Старые
   App ID и группа остаются на портале и ничему не мешают.
3. Ключ — как в гейте M4 (пункты 1 и 3 этапа E). Профиль в Настройки → VPN появляется только после
   «Разрешить» и называется «OVoC Client».
4. `make logs` читает уже новую App Group; в Console.app — фильтр `subsystem:com.razhev.ovocclient`.

**Пройдено 2026-09-24** (iPhone 16 Pro, iOS 26.6.2): `make install` выпустил профиль «iOS Team
Provisioning Profile: com.razhev.ovocclient», оба `PASS подпись` с `group.com.razhev.ovocclient`;
первый запуск — `load: profiles=0 appGroup=ok`; импорт вставкой — `import OK: profile=8882 bytes`;
`event: connected` через Cloak, `heartbeat: memory=8 MB` с пакетами в обе стороны, без
`Transport error`.
